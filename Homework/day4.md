## Q1 微调的整体流程（1.2 / 1.3）

**0. 先判断需不需要微调（1.2）**

微调不能解决所有问题。模型效果不好，可能是任务描述不清楚、缺少外部知识、基础能力不足，或者行为不符合要求。应该**从轻到重**依次尝试：

```
直接用模型 + 简单 prompt
  → 不行：优化提示词（Prompt Engineering）
  → 不行：加示例（ICL / few-shot）
  → 不行：收集数据，判断问题类型
        ├─ 缺知识（实时、私有、需要引用来源）→ RAG
        ├─ 行为不对（格式、流程、术语、表达方式）→ 监督微调 SFT
        └─ 领域语言差距太大，并且有资源 → 继续预训练
```

| 方法 | 改不改参数 | 适合解决 |
|---|---|---|
| 提示词工程 | 不改 | 成本最低、迭代最快，**优先尝试** |
| RAG | 不改 | 实时知识、私有知识、需要引用来源 |
| 监督微调 | 改 | 稳定输出格式、任务流程、术语和表达方式 |
| 继续预训练 | 改 | 让模型适应领域的语言分布（需要大量领域文本） |

**1. 确定要微调后，一个项目的五个环节（1.3）**

| 环节 | 要做的事 | 产出 |
|---|---|---|
| ① **模型选择** | 根据任务、语言、规模、训练资源和许可证选候选模型，在目标任务上做**基线评测** | 基础模型 + 基线分数 |
| ② **数据准备** | 收集示范数据，清洗、统一格式（messages）、划分训练/验证/测试集、检查质量 | train / validation / test.jsonl |
| ③ **方法选择** | 根据资源和效果要求，选全参微调、LoRA 或 QLoRA，估算显存并选卡 | 训练方案 + 硬件 |
| ④ **模型训练** | 运行训练，记录 loss、梯度、显存、checkpoint 和实验配置 | 最佳 checkpoint / Adapter |
| ⑤ **效果评测** | 用**同一个测试集、同样的生成参数**对比微调前后；同时检查**通用能力**有没有下降 | 评测报告 |

**口述版**：先判断问题是不是微调能解决的，能用提示词或 RAG 解决就不微调。确定要微调后，先选一个和任务匹配的基础模型，在测试集上测出基线；然后准备高质量的 messages 格式数据并划分数据集；根据显存和效果要求选择全参、LoRA 或 QLoRA；训练时盯着 loss 和验证集指标，保存最佳 checkpoint；最后在同一测试集上对比微调前后的效果，并确认通用能力没有明显下降。

> 我们的实操案例：Qwen3-0.6B 做意图识别和槽位提取，指标是 Joint Exact Match（意图和槽位全部正确才算对）。流程依次是：基线测试 → 全参微调 / LoRA / QLoRA → 在同一个 test.jsonl 上评测（6.2.3）。

## Q2 模型选择方法论（2）

**1. 三个选型因素**

**① 模型类型：Base 还是 Instruct**

| | Base Model | Instruct Model |
|---|---|---|
| 来源 | 只做了预训练 | 在 Base 基础上做了指令微调和偏好对齐 |
| 能力 | 有语言能力和知识，但不一定能稳定执行指令 | 已经能理解指令、进行对话 |
| 从它开始微调 | 既要学任务，又要学「怎么听指令、怎么回答」，需要**更多、更全面**的数据 | 只需在已有能力上调整术语、格式和流程，**数据需求少** |
| 什么时候选 | 需要自己构建指令能力，或者 Instruct 模型的已有行为和目标任务明显冲突 | **问答、抽取、生成、结构化输出等，优先选它** |

**② 模型系列**：Qwen（中文、多语言、规模选择多）、DeepSeek、GLM、Kimi、Llama（生态好）、Mistral、Gemma（轻量）等。

可以参考的榜单：OpenCompass（中文和综合能力）、Artificial Analysis（能力与成本）、LiveBench（新题，减少数据污染）、Arena（用户盲测偏好）。**榜单只用于初筛**，要看和任务相关的分项成绩，最终以在自己任务上的实际表现为准。

**③ 参数规模**

| 场景 | 参考规模 |
|---|---|
| 分类、抽取、改写、格式转换 | 1.5B～7B |
| 客服问答、总结、内容生成 | 7B～14B |
| 领域问答、多步骤任务、代码生成 | 14B～32B |
| 复杂推理、开放式任务 | 32B～70B 及以上 |

模型越大，能力越强，但训练和**推理成本**也越高。参数量不等于能力，结构不同的模型不能直接按参数量比较。

**2. 选型三步法（2.3）**

1. **确定候选**：根据任务要求和资源限制，排除明显不合适的，保留少量候选。
2. **基线评测**：所有候选用**相同的样本、相同的 prompt、各自推荐的生成参数**来测，检查：
   - 是否理解任务；是否基本正确；困难样本和边界样本处理得如何；格式和流程是否稳定。
   - **核心部分都做不好 → 换模型**；能基本完成、只是格式或流程不稳定 → **适合作为微调候选**。
   - 基线分数同时也是之后判断「微调有没有用」的参照。
3. **确定最终模型**：在效果达标的候选中，**优先选资源成本低、工具链成熟的**。

## Q3 🌟🌟🌟 数据工程与数据构造方式（3）

**0. 核心观点**

训练数据决定了模型学什么任务、遵循什么规则、怎么回答。**数据里的错误、矛盾、重复和偏差，模型都会学进去。** 所以**质量比数量更重要**：准确、一致、符合任务要求，才能让模型形成稳定可靠的行为。

**1. 三种数据构造方式（3.2）**

| 方式 | 做法 | 优点 | 注意点 |
|---|---|---|---|
| **① 线上数据回流** | 项目初期先用线上大模型处理真实请求，通过日志记录用户 prompt、必要的上下文和模型回答，积累后整理成训练样本 | 数据**最贴近真实分布**，覆盖用户的真实说法 | 回答质量取决于原模型，需要**人工审核和修正**；注意隐私脱敏 |
| **② 已有数据转换** | 把企业内部文档（Markdown、PDF、DOCX、TXT）切块，用大模型从每块生成问题，再结合原文生成答案，组成单轮或多轮问答。工具：**EasyDataset**，生成后人工审核，再导出成微调格式 | 能把**私有知识**变成训练数据，自动化程度高 | 切块要合理；问题要多样；答案必须忠于原文，防止编造 |
| **③ 种子数据扩写** | 人工或业务专家先写**结构化的种子**（JSON），说明场景、目标、要点和约束；再让**强模型**基于每个种子扩写出多个不同表达、不同场景的变体（单轮或多轮） | 数量可以快速放大，**多样性好**，模型能学到「同一任务的不同说法」，泛化更好 | 种子质量决定上限；扩写结果要抽查，防止偏离约束 |

种子数据示例（讲义）：

```json
{
  "场景": "车机蓝牙无法连接",
  "用户目标": "完成手机与车机蓝牙配对",
  "必要事实": ["手机蓝牙已开启", "车机蓝牙已开启"],
  "客服要求": ["确认手机型号", "指导删除旧配对记录后重新连接"]
}
```

用这一个种子，可以扩写出单轮回答，也可以扩写出「先问机型 → 确认蓝牙已开 → 指导删除旧配对」这样的多轮对话。

**2. 统一的对话数据格式（3.3）**

```json
{"messages": [
  {"role": "system",    "content": "你是一个信息抽取助手。"},
  {"role": "user",      "content": "从下面文本中抽取人物和地点：李明周一到达杭州。"},
  {"role": "assistant", "content": "人物：李明；地点：杭州。"}
]}
```

| role | 内容 |
|---|---|
| system | 身份、任务和规则，可以省略 |
| user | 指令、问题和完成任务需要的输入。分类、抽取类任务通常把**任务说明和原文都放在 user** 里 |
| assistant | **要让模型学的目标回答**，标签或结构化结果放在这里 |

- 多轮对话按真实顺序保存多组 user 和 assistant。
- **messages 只是逻辑结构**，不是模型实际看到的文本。真正输入模型前，要由各模型自己的 **chat_template** 转换成带特殊 token 的文本。所以训练和推理必须使用同一个模板。

**3. 数据处理流程（补充，结合我们的案例）**

1. **收集**：用上面三种方式获取原始数据。
2. **清洗**：去重、去掉空回答或乱码、修正错误标注、脱敏，统一术语和格式。例如 JSON 输出要能被解析，槽位值必须从原文中原样复制。
3. **转换格式**：统一成 messages。我们的案例中，原始数据是 `{text, intent, slots}`，用 `build_messages(sample, include_answer=True)` 拼上 system prompt 和 assistant 答案。
4. **划分**：训练集用来更新参数，验证集用来选最佳 checkpoint，测试集**只用于最终评测，不能参与训练**（案例中是 11514 / 2033 / 2974 条）。
5. **检查**：标签分布是否均衡、难例和边界样本是否覆盖、有没有和测试集重复的样本。
6. **防止遗忘**（补充）：如果担心通用能力下降，可以混入少量通用对话数据。

## Q4 LoRA 的原理和配置参数（4.2）

**1. 原理**

全参微调学的是一个完整的增量：$W = W_0 + \Delta W$，前向计算 $y = xW_0 + x\Delta W$。

LoRA 的作者发现 **$\Delta W$ 往往是低秩的**，所以用两个小矩阵的乘积来近似：

$$
\Delta W \approx AB,\quad A\in\mathbb{R}^{d\times r},\ B\in\mathbb{R}^{r\times k},\quad r \ll \min(d,k)
$$

- **训练时**：$W_0$ **冻结**，只训练 $A$ 和 $B$，前向计算为 $y = xW_0 + \frac{\alpha}{r}\,xAB$。
- **推理时**有两种方式：
  - 保留分支：$y = xW_0 + xAB$，可以随时切换或卸下 Adapter；
  - **合并**：$W = W_0 + AB$，合并后就是一个普通线性层，**推理没有额外开销**。
- **参数量**：全参需要 $dk$，LoRA 只需要 $r(d+k)$。

补充（LoRA 论文的初始化）：$A$ 用随机高斯初始化，$B$ 初始化为 0。这样训练开始时 $AB=0$，模型行为和原模型完全一样，训练从原模型平滑开始。

> 附录 9.1：秩等于线性无关的行（列）的最大个数。秩为 r 的矩阵可以分解为 $W=AB$。$A$ 的列提供独立的方向，$B$ 给出这些方向的组合系数。

**补充：算一下 Qwen3-0.6B 用 r=8、7 个模块时的可训练参数**（hidden 1024，intermediate 3072，16 个 Q 头 + 8 个 KV 头，head_dim 128，28 层）

| 模块 | 形状 d×k | r(d+k) |
|---|---|---|
| q_proj | 1024×2048 | 24,576 |
| k_proj / v_proj | 1024×1024 | 16,384 × 2 |
| o_proj | 2048×1024 | 24,576 |
| gate_proj / up_proj | 1024×3072 | 32,768 × 2 |
| down_proj | 3072×1024 | 32,768 |
| **每层合计** | | **180,224** |
| **× 28 层** | | **≈ 5.05M**，约占总参数（≈0.6B）的 **0.8%** |

运行 `peft_model.print_trainable_parameters()` 时，打印出的数字应该和这个量级一致。

**2. 配置参数（4.2.3）**

| 参数 | 含义 | 常用值 / 经验 |
|---|---|---|
| `r` | 低秩矩阵的秩。越大表达能力越强，参数也越多 | 4/8/16/32/64；**先从 8 或 16 开始**。简单任务用小一点，复杂任务调大 |
| `lora_alpha` | 缩放系数 $\alpha$。实际增量是 $\frac{\alpha}{r}AB$，$1/r$ 用来抵消 r 的影响，$\alpha$ 控制 LoRA 分支整体的作用强度 | 通常取 $\alpha = 2r$，例如 r=8 对应 α=16，r=16 对应 α=32 |
| `target_modules` | 把 LoRA 插到哪些线性层 | 注意力层：`q_proj k_proj v_proj o_proj`；FFN：`gate_proj up_proj down_proj`。覆盖的模块越多，效果通常越好，参数也越多。也可以写 `"all-linear"`。**不同模型的层名不同，要先看模型结构** |
| `lora_dropout` | LoRA 分支输入端的 Dropout，用于防止过拟合 | 0 / 0.05 / 0.1，**先用 0.05**。数据多就设 0，数据少或过拟合就设 0.1 |
| `task_type` | 任务类型 | 因果语言模型用 `TaskType.CAUSAL_LM` |
| `bias` | 是否训练 bias | 一般用 `"none"` |

**3. 和全参微调的对比**

| | 全参微调 | LoRA |
|---|---|---|
| 训练参数 | 全部 | 约 0.1%～1% |
| 显存 | $18P$ | $2P + 18T$（见 Q6） |
| 学习率 | 小，例如 2e-5 | 大，例如 1e-4～3e-4（讲义用 1e-4） |
| 保存产物 | 完整模型 | 只有 Adapter（`adapter_model.safetensors` + `adapter_config.json`），几 MB 到几十 MB |
| 推理开销 | 无 | 合并后无 |

## Q5 QLoRA 的原理：NF4 和另外两个技术点（4.3）

**1. 动机**

LoRA 已经把梯度和优化器状态降到很小，但**冻结的基础模型仍然要以 BF16 完整加载**，模型越大，这部分越成为主要的显存开销。QLoRA 的做法是：**基础模型的线性层用 4-bit 存储并冻结，LoRA 参数用较高精度训练**。

**2. 量化基础（4.3.2）**

4-bit 有 16 个编码，每个编码对应一个量化点。量化过程：

- 每块权重取最大绝对值 $s = \max|w_i|$，归一化 $z_i = w_i / s$，落在 [-1, 1] 之间；
- 映射到最近的量化点，保存它的编码（4 bit），同时保存 $s$。
- 反量化：编码 → 量化点 × $s$，和原值的差就是量化误差。
- **分块量化**：如果整个张量共用一个 $s$，个别极端值会让所有其他值的精度变差，所以要**分块**，每块各有一个 $s$。块越小，误差越小，但 $s$ 越多。

讲义例子：`[0.27, 0.58, -0.75, 1.52]` → 除以 1.52 → 找最近的量化点 → 编码 `9,10,4,15` → 反量化得到 `0.304, 0.5016, -0.7144, 1.52`。

**3. 三项技术**

**① NF4（4-bit NormalFloat）**

- 问题：预训练权重**近似服从均值为 0 的正态分布**，大部分在 0 附近，绝对值大的很少。均匀量化在两端（数据很少）放了很多格点，在 0 附近（数据密集）格点不够。
- 做法：按**标准正态分布的累积概率等分成 16 个区间**，每个区间取中位数作为量化值。
- 效果：**0 附近格点密、两端格点疏**，和权重分布匹配，量化误差更小。补充：这是一种在信息论意义上最优的分位数量化，每个编码被用到的概率大致相同。

**② 双重量化（Double Quantization）**

- 问题：块不能太大，所以缩放因子非常多。如果全部用 FP32 保存，本身就占不少显存。
- 做法：**对缩放因子再量化一次**，每 256 个缩放因子为一组，用 8-bit 保存。
- 补充（QLoRA 论文的数字）：块大小为 64 时，FP32 缩放因子平均每个参数占 32/64 = 0.5 bit；双重量化后约 8/64 + 32/(64×256) ≈ 0.127 bit。**每个参数省约 0.37 bit**，65B 模型约省 3GB。

**③ 分页优化器（Paged Optimizer）**

- 利用 NVIDIA 统一内存，以**页**为单位管理优化器状态。显存紧张时，自动把一部分页换到 **CPU 内存**；需要时再换回 GPU。
- 作用是**用 CPU 内存缓冲短时的显存峰值，防止 OOM**。它会带来数据传输开销，**目的是让训练能跑起来，不是为了加速**。
- 对应代码：`optim="paged_adamw_8bit"`（讲义）或 `"paged_adamw_32bit"`。

**4. 代码要点（6.4.2）**

```python
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,                      # 4-bit 加载
    bnb_4bit_quant_type="nf4",              # ① NF4
    bnb_4bit_use_double_quant=True,         # ② 双重量化
    bnb_4bit_compute_dtype=torch.bfloat16,  # 计算时反量化成 BF16
)
model = AutoModelForCausalLM.from_pretrained(path, quantization_config=bnb_config)
model = prepare_model_for_kbit_training(model)   # 冻结全部参数；未量化的参数转成 FP32，提高稳定性
peft_model = get_peft_model(model, lora_config)  # 注入 LoRA
SFTConfig(..., optim="paged_adamw_8bit")         # ③ 分页优化器
```

- **只量化线性层**，Embedding、LayerNorm 和部分输出层保持高精度。
- 评估时要用**同样的 bnb_config** 加载；合并时要先用 **BF16 重新加载**基础模型，再 `merge_and_unload()`，因为 LoRA 增量不能直接加到 4-bit 权重上。

## Q6 显卡选型：显存构成和静态显存估算（5）

**1. 显卡的基本知识（5.1 / 5.2）**

- 显卡由**计算单元**（GPU 芯片）和**显存**组成。显存只负责存放数据，计算由计算单元完成。
- 训练速度 = **计算能力** + **显存与计算单元之间的传输速度**。

| 指标 | 含义 |
|---|---|
| TFLOPS | 每秒万亿次浮点运算，**要看是哪种精度**（FP32、BF16、FP8 差别很大） |
| TOPS | 每秒万亿次整数运算（INT8、INT4），多用于量化推理 |
| **显存容量** | 决定**能不能训练**：模型、梯度、优化器状态、激活值必须同时放得下 |
| 显存带宽 | 决定数据搬运速度，带宽越高，计算单元等数据的时间越短 |

常见卡：3090 和 4090 是 24GB，5090 是 32GB，A100 是 40GB 或 80GB，H100 是 80GB，H200 是 141GB。

**2. 训练显存的构成（5.4.1）**

$$
M_{train} \approx \underbrace{M_{weight} + M_{gradient} + M_{optimizer}}_{\text{静态显存：可以用公式估算}} + \underbrace{M_{activation} + M_{runtime}}_{\text{很难事先算准}}
$$

| 组成 | 取决于 |
|---|---|
| 权重、梯度、优化器状态 | 参数量、训练精度、优化器类型 |
| 激活值 | batch 大小、序列长度、模型结构、是否开梯度检查点 |
| 运行时开销 | 临时张量、通信缓冲区、CUDA 上下文、显存碎片 |

**3. 静态显存估算（BF16 混合精度 + AdamW）**

**全参微调：每个参数 18 字节**

| 组成 | 字节 |
|---|---|
| BF16 参数 | 2 |
| FP32 参数副本 | 4 |
| 梯度 | 4 |
| AdamW 一阶矩和二阶矩 | 8 |
| **合计** | **18** |

$$
M_{full} \approx 18P,\qquad M_{LoRA} \approx 2P + 18T,\qquad M_{QLoRA} \approx M_{4bit\ base} + 18T
$$

**补充：用 Qwen3 系列算一下（只算静态部分）**

| 模型 | 全参 18P | LoRA 2P + 18T | QLoRA |
|---|---|---|---|
| Qwen3-0.6B | ≈ 10.8 GB | ≈ 1.2 GB + 0.1 GB | ≈ 0.6 GB |
| Qwen3-4B | ≈ 72 GB | ≈ 8 GB + 0.3 GB | ≈ 2.5～3 GB |
| Qwen3-8B | ≈ 148 GB | ≈ 16.4 GB + 0.4 GB（r=8 时 T≈22M） | ≈ 5.5～6 GB |

（QLoRA 的基础模型部分按「线性层 0.5 字节/参数 + embedding 和 lm_head 保持 BF16」估算。）

- 所以 Qwen3-4B **全参**微调单张 5090（32GB）放不下，讲义里用了 **4 卡 + ZeRO-3**（见 day5）。
- LoRA **不会按比例减少激活值**，batch 大或序列长时仍然可能 OOM，需要配合梯度检查点、减小 batch 或使用梯度累积。

**4. 选卡流程（5.4.2）**

1. 根据微调方式算出单卡需要的静态显存；
2. 选显存够用、并且**留有余量**（用于激活值和运行时开销）的候选卡；
3. **用正式的训练配置实际跑一个 step**，看真实显存占用；
4. 结合测试结果、租用价格和可用性，最终确定。

## Q7 SFTTrainer 和 SFTConfig 的参数（6.2.2，代码见 [sft/src/train_lora.py](../sft/src/train_lora.py)）

**1. 工具链（6.1.1）**

PyTorch（底层计算）→ Transformers（模型和 Tokenizer）→ Datasets（数据）→ **TRL（SFTTrainer 组织训练）** → PEFT（LoRA）→ bitsandbytes（4-bit 量化）。

**2. SFTTrainer 的构造参数**

| 参数 | 含义 |
|---|---|
| `model` | 模型对象或模型名称字符串（传字符串时会自动加载） |
| `args` | `SFTConfig` 实例 |
| `train_dataset` / `eval_dataset` | 训练集和验证集，每条样本有 `messages` 字段（也支持 `prompt`/`completion` 格式） |
| `processing_class` | tokenizer |
| `peft_config` | 传入 `LoraConfig` 后会**自动注入 LoRA**，可以不手动调用 `get_peft_model` |
| `data_collator` / `formatting_func` / `callbacks` | 自定义拼批、格式化、回调（补充，按需使用） |

**3. SFTConfig 常用参数（按用途分组）**

**数据相关**

| 参数 | 含义 | 案例取值 |
|---|---|---|
| `max_length` | 单条样本截断长度（token 数），超过部分会被截掉 | 1024（讲义），我的代码是 10240 |
| `assistant_only_loss` | **只对 assistant 部分计算 loss**，system 和 user 部分不算。要求 chat template 里有 `{% generation %}` 标记，所以我的代码用了 `chat_template_path` 指定新模板 | True |
| `packing`（补充） | 把多条短样本拼接到一个序列里，提高利用率 | 默认 False |

**训练规模**

| 参数 | 含义 |
|---|---|
| `num_train_epochs` | 训练轮数 |
| `per_device_train_batch_size` | **每张卡**每一步的 batch 大小 |
| `gradient_accumulation_steps` | 梯度累积步数：累积 N 步再更新一次参数，用时间换显存 |
| 实际全局 batch | = `per_device_train_batch_size × gradient_accumulation_steps × GPU 数`。讲义例子 8 × 2 × 1 = 16 |

**优化器和学习率**

| 参数 | 含义 | 经验值 |
|---|---|---|
| `learning_rate` | 学习率 | 全参 2e-5；LoRA 1e-4～3e-4 |
| `warmup_steps` / `warmup_ratio` | 学习率预热，前若干步从 0 线性升到目标值，避免一开始更新过猛 | 我的代码写了 `warmup_steps=0.1`。较新版本的 transformers 会把小于 1 的值当作比例；**老版本要求整数，应改用 `warmup_ratio=0.1`**，以所装版本为准 |
| `lr_scheduler_type`（补充） | 学习率衰减方式 | 默认 linear，也常用 cosine |
| `weight_decay` | 权重衰减（L2 正则），防止过拟合 | 0.01 |
| `optim` | 优化器 | 默认 adamw；`adamw_torch_fused` 更快；QLoRA 用 `paged_adamw_8bit` |

**精度和显存**

| 参数 | 含义 |
|---|---|
| `bf16` / `fp16` | 混合精度训练，30/40/50 系、A100 等推荐用 bf16 |
| `bf16_full_eval` | 评估时整体用 bf16，省显存 |
| `gradient_checkpointing` | **梯度检查点**：前向时不保存中间激活值，反向时重新计算。约多花 30% 时间，换来激活值显存大幅下降 |

**日志、评估和保存**

| 参数 | 含义 |
|---|---|
| `logging_strategy` / `logging_steps` | 每多少步记录一次 loss |
| `report_to` | 日志写到哪里，例如 `"tensorboard"`、`"wandb"` |
| `eval_strategy` / `eval_steps` | 每多少步在验证集上评估一次 |
| `save_strategy` / `save_steps` | 每多少步保存一次 checkpoint |
| `save_total_limit` | 最多保留几个 checkpoint，旧的会被删除 |
| `load_best_model_at_end` | 训练结束后**加载验证集上最好的 checkpoint**。要求 save 和 eval 的策略一致，且 `save_steps` 是 `eval_steps` 的整数倍 |
| `metric_for_best_model` / `greater_is_better` | 用哪个指标判断「最好」。用 `eval_loss` 时搭配 `greater_is_better=False`（越小越好） |
| `output_dir` | checkpoint 输出目录 |

**4. 最简用法**

```python
trainer = SFTTrainer(model="Qwen/Qwen3-0.6B",
                     args=SFTConfig(output_dir="./out", num_train_epochs=1,
                                    per_device_train_batch_size=1, max_length=512),
                     train_dataset=load_dataset("trl-lib/Capybara", split="train[:1000]"))
trainer.train()
trainer.save_model("./out/final")
```

完整参数以 [TRL 官方文档](https://huggingface.co/docs/trl/sft_trainer) 为准，不同版本之间参数名可能有变化（例如 `max_seq_length` 改成了 `max_length`）。
